## 概述

**Agent 集群（Agent Cluster）** 是把多个 LLM Agent 实例作为一组可调度、可伸缩、可观测的计算单元统一编排与运行的系统。它把单个 Agent 的「一次对话/一个任务」升级为「大规模并发、跨节点协作、可持续运行」的服务能力。

一句话概括：

> **单 Agent 解决「一个任务怎么做对」，Agent 集群解决「成千上万个任务如何又快又稳又省地同时做对」。**

本文从概念、架构、子系统、部署、伸缩、优化、优缺点等维度给出一份可落地的工程文档。

## 什么是 Agent 集群

Agent 集群不是简单地「多开几个 Agent」，而是一套围绕 Agent 生命周期的分布式系统。它通常包含以下角色：

| 角色 | 职责 |
|------|------|
| **Orchestrator（编排器）** | 接收任务、拆解任务、分发给 Worker、聚合结果 |
| **Worker Agent（工作节点）** | 真正执行推理 + 工具调用的 Agent 实例 |
| **Scheduler（调度器）** | 决定任务分配到哪个节点、控制并发与优先级 |
| **State Store（状态存储）** | 保存会话、任务、上下文、检查点 |
| **Message Bus（消息总线）** | Agent 间/节点间异步通信 |
| **Tool Gateway（工具网关）** | 统一代理外部工具/API/MCP 调用与鉴权 |
| **Memory Layer（记忆层）** | 长期记忆、向量检索、共享知识 |
| **Observability（可观测层）** | 日志、指标、Trace、成本与轨迹回放 |

### 与相邻概念的区别

| 概念 | 关注点 | 关系 |
|------|--------|------|
| **单 Agent** | 单次任务的推理循环（Agent Loop） | 集群的最小单元 |
| **Multi-Agent 编排** | 多个角色 Agent 如何协作分工（Planner/Coder/Reviewer） | 集群内的「逻辑协作模式」 |
| **Agent 集群** | 大量 Agent 实例的运行时调度、伸缩、容错 | 承载 Multi-Agent 的「物理运行底座」 |

> Multi-Agent 是编排层的「怎么分工」，Agent 集群是基础设施层的「怎么把这些分工跑起来、跑得住、跑得起」。

## 解决什么问题

单实例 Agent 在生产环境会遇到一系列瓶颈，集群化正是为解决它们而生：

| 问题 | 单 Agent 的痛点 | 集群的解法 |
|------|----------------|-----------|
| **吞吐瓶颈** | 单进程串行处理，任务排队 | 水平扩展多 Worker 并行消费 |
| **长任务阻塞** | 一个耗时任务占满资源 | 任务隔离、独立节点、超时熔断 |
| **可用性** | 单点崩溃全部不可用 | 多副本 + 健康检查 + 故障转移 |
| **上下文膨胀** | 单 Agent 塞入所有上下文导致 Context Rot | 任务拆分 + 专用子 Agent 各自窄上下文 |
| **成本失控** | 无预算约束，Token/工具调用无上限 | 集中式预算、限流、缓存复用 |
| **异构负载** | 简单/复杂任务混在一起 | 分层路由：小模型处理简单任务，大模型处理复杂任务 |
| **状态丢失** | 进程重启丢失会话 | 外置状态存储 + 检查点恢复 |
| **协作复杂** | 难以协调多角色 Agent | 统一消息总线 + 编排器 |
| **可观测性差** | 黑盒，难定位问题 | 全链路 Trace + 轨迹回放 |

典型适用场景：

- **大规模批处理**：批量代码审查、批量文档生成、批量数据标注。
- **高并发在线服务**：客服 Agent、编程助手后端，需要同时服务大量用户。
- **复杂长流程**：需要 Planner → 多个 Coder → Reviewer 协作的深度任务。
- **异步任务队列**：用户提交任务后台跑，完成后回调。

## 核心概念与拓扑

Agent 集群常见的组织拓扑：

### 1. 中心化编排（Orchestrator-Worker）

```
                    ┌──────────────┐
        Task ─────▶ │ Orchestrator │  拆解 & 分发 & 聚合
                    └──────┬───────┘
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │ Worker1 │  │ Worker2 │  │ Worker3 │   同构/异构 Agent
        └─────────┘  └─────────┘  └─────────┘
```

- 优点：控制强、易聚合、易追踪。
- 缺点：编排器是瓶颈/单点，需做高可用。
- 适用：任务可拆解为独立子任务（Map-Reduce 风格）。

### 2. 分层编排（Hierarchical）

```
        Lead Agent（规划）
          ├── Sub-Orchestrator A ── Workers...
          └── Sub-Orchestrator B ── Workers...
```

- 优点：可扩展到大规模、分而治之。
- 适用：超大任务、多领域协作。

### 3. 去中心化 / 事件驱动（Choreography）

```
   Agent A ──event──▶ Bus ◀──event── Agent B
                      ▲  │
                      │  ▼
                    Agent C（订阅感兴趣的事件）
```

- 优点：解耦、弹性好、无单点。
- 缺点：全局状态难追踪、调试复杂。
- 适用：松耦合的自治 Agent 生态。

### 4. 黑板模式（Blackboard）

多个 Agent 读写同一共享状态区（Blackboard），各自在合适时机贡献结果。适合探索式、非确定性协作。

## 关键子系统设计

### 1. 调度与负载均衡

调度器是集群性能的核心，需要处理 Agent 任务特有的属性：**执行时间高度不确定（几秒到几十分钟）、消耗资源异构（Token/内存/工具配额）**。

**调度策略：**

| 策略 | 说明 | 适用 |
|------|------|------|
| **队列 + 优先级** | 高优任务插队，普通任务排队 | 通用 |
| **模型分层路由** | 简单任务 → 小模型/廉价模型；复杂任务 → 大模型 | 成本优化 |
| **亲和性路由** | 同一会话/项目路由到同节点，复用缓存/上下文 | 有状态任务 |
| **公平调度** | 按租户/用户配额分配，避免饿死 | 多租户 |
| **背压 (Backpressure)** | 队列过长时拒绝/降级新任务 | 过载保护 |

**并发控制要点：**

- 每个 Worker 有最大并发数（受内存与上游 LLM 速率限制约束）。
- 全局限制上游 LLM API 的 RPM/TPM，避免触发 429。
- 用令牌桶对「每租户 Token 预算」做限流。

```
任务入队 → 检查全局/租户配额 → 选择模型层级 → 选择空闲 Worker
       → 执行 → 超时熔断 → 结果回写 → 释放配额
```

### 2. 状态与上下文管理

Agent 必须**无状态化运行时 + 外置状态**，才能水平扩展与故障恢复。

- **会话状态外置**：对话历史、任务进度存 Redis/DB，而非进程内存。
- **检查点（Checkpointing）**：长任务在关键步骤落盘，崩溃后从检查点恢复而非重跑。
- **上下文预算**：每个子 Agent 只加载与其任务相关的窄上下文，避免 Context Rot。
- **上下文压缩**：长历史做摘要/裁剪后再传递（见本仓 `context-management-system-practical-guide.md`）。

> 关键原则：**Worker 可以随时被杀死重建，状态永远在集群的存储层，而不在某个进程里。**

### 3. 消息与通信总线

Agent 间通信推荐**异步消息**而非同步 RPC，以获得解耦与弹性：

| 机制 | 用途 |
|------|------|
| **消息队列**（Kafka/RabbitMQ/NATS） | 任务分发、事件广播、结果回传 |
| **Pub/Sub** | 事件驱动协作、状态变更通知 |
| **共享状态**（Redis/Blackboard） | 协作中间结果、进度同步 |
| **直接调用** | 编排器 → Worker 的同步子调用（需超时+重试） |

通信内容要标准化：任务 ID、父任务 ID、上下文引用（而非内联大对象）、幂等键。

> 传递「引用」而非「全量数据」：大上下文存对象存储，消息里只带指针，避免消息体膨胀。

### 4. 工具与资源治理

集群里成百上千 Agent 会同时打外部工具/API，必须集中治理：

- **工具网关（Tool/MCP Gateway）**：统一代理所有工具调用，做鉴权、限流、审计。
- **权限分层**：不同 Agent 角色拥有不同工具权限（最小权限原则）。
- **配额与熔断**：对下游 API 做熔断，防止级联故障。
- **结果缓存**：相同工具调用结果缓存复用，降本增效。

（可参考本仓 `ai-observability-agent-gateway-governance.md` 与 `ai-production-permission-system-four-layer-defense.md`。）

### 5. 记忆与知识层

- **短期记忆**：当前任务上下文（会话级）。
- **长期记忆**：跨任务的用户偏好、历史结论，向量库存储 + 检索。
- **共享知识**：集群级知识库，多 Agent 共享（RAG）。
- **记忆一致性**：并发写入需版本控制/锁，避免脏写。

### 6. 可观测性与追踪

Agent 集群是分布式 + 非确定性系统，**没有可观测性就无法运维**。

- **分布式 Trace**：一个用户请求跨编排器→多 Worker→工具调用的完整链路（OpenTelemetry）。
- **Agent 轨迹回放**：记录每步推理、工具调用、输入输出，可完整复现。
- **核心指标**：任务成功率、P95 时延、每任务 Token/成本、工具调用失败率、队列深度、Worker 利用率。
- **告警**：成本突增、成功率下跌、队列积压、循环未收敛。

### 7. 容错与自愈

| 故障 | 应对 |
|------|------|
| Worker 崩溃 | 健康检查 + 自动重启 + 任务从检查点重派 |
| LLM API 超时/429 | 重试（指数退避）+ 降级到备用模型 |
| Agent 死循环 | 步数上限 + Token 预算 + 超时熔断（三道保险丝）|
| 编排器单点 | 多副本 + Leader 选举 + 状态外置 |
| 任务卡死 | 心跳检测 + 超时回收 + 重新调度 |
| 下游级联故障 | 熔断器 + 舱壁隔离（Bulkhead）|

> Agent Loop 的失控是集群特有风险，务必设置「终止控制 + 失败学习 + Token 预算」三道保险（见本仓 `agent-loop-three-fuses.md`）。

## 部署方案

### 容器化 + Kubernetes（主流）

```
┌────────────── Kubernetes 集群 ──────────────┐
│  Deployment: orchestrator (2+ 副本, HA)      │
│  Deployment: worker-agent (HPA 自动伸缩)     │
│  Deployment: tool-gateway                    │
│  StatefulSet / 外部托管: Redis, 向量库, MQ   │
│  Service + Ingress: 接入层                    │
│  HPA / KEDA: 按队列深度伸缩 Worker            │
│  ConfigMap/Secret: 模型 Key、Prompt 模板      │
└──────────────────────────────────────────────┘
```

**要点：**

- **Worker 无状态**：Pod 可随意扩缩，状态全在外置存储。
- **KEDA 按队列长度伸缩**：比 CPU 指标更贴合 Agent 负载（Agent 大部分时间在等 LLM 响应，CPU 低但任务多）。
- **资源限制**：给每个 Worker 设内存上限，防止上下文膨胀 OOM。
- **优雅关闭**：收到 SIGTERM 时完成当前任务或落检查点再退出。

### Serverless / 函数计算

- 适合突发、事件驱动、单任务时长可控的场景。
- 优点：零闲置成本、自动伸缩到零。
- 缺点：冷启动、执行时长上限（长任务需拆分或用长运行方案）。

### 混合部署

- 编排器/网关 → 常驻服务（K8s Deployment）。
- Worker → 按负载 Serverless 或 K8s HPA。
- 状态/记忆/MQ → 托管云服务（降低运维负担）。

### 部署对比

| 方案 | 弹性 | 成本 | 运维复杂度 | 适用 |
|------|------|------|-----------|------|
| K8s + HPA/KEDA | 高 | 中 | 中高 | 稳定高并发生产 |
| Serverless | 极高（缩到 0）| 按需 | 低 | 突发/事件驱动 |
| 混合 | 高 | 优 | 中 | 大多数生产场景 |
| 单机多进程 | 低 | 低 | 低 | 原型/小规模 |

## 弹性伸缩策略

Agent 负载与传统 Web 服务不同：**CPU 低、等待多、单任务重、时长方差大**。因此伸缩指标应选：

- **队列深度 / 待处理任务数**（首选，用 KEDA）。
- **平均任务等待时间**（SLA 驱动）。
- **上游 LLM 速率余量**（避免扩了 Worker 却被 API 限流）。

```
队列积压上升 → KEDA 触发 → 扩 Worker → 消费加速
队列清空 → 缩容（保留最小副本，避免冷启动抖动）
```

**注意事项：**

- 设置**最小副本数**，避免频繁冷启动。
- 伸缩要考虑**上游瓶颈**：LLM API 配额才是真正天花板，盲目扩 Worker 只会撞 429。
- **预热**：大模型客户端连接池、缓存预热，减少首任务延迟。

## 成本与性能优化

Agent 集群成本主要在 **LLM Token** 与 **工具调用**，优化手段：

| 手段 | 说明 |
|------|------|
| **模型分层** | 简单任务用小/廉价模型，复杂任务才用大模型 |
| **Prompt/KV 缓存** | 复用系统提示、公共上下文的缓存（见 `cache-explained-and-cost-control.md`）|
| **上下文压缩** | 裁剪、摘要历史，减少输入 Token |
| **结果缓存** | 相同任务/工具调用结果复用 |
| **批处理** | 合并同类请求，提高吞吐 |
| **并行拆解** | 任务并行以缩短端到端时延 |
| **预算护栏** | 每任务/每租户 Token 上限，超限熔断 |
| **投机/小模型草稿** | 小模型先草拟，大模型校验 |

## 有什么优点

1. **高吞吐**：水平扩展，N 个 Worker 并行消费，任务处理能力随节点线性增长。
2. **高可用**：多副本 + 故障转移，单节点崩溃不影响整体服务。
3. **弹性伸缩**：按负载自动扩缩，高峰扩容、低谷缩容甚至到零，成本随用量走。
4. **任务隔离**：一个任务的失败/超时/死循环不拖垮其他任务。
5. **专注与解耦**：每个 Agent 窄上下文、专职专用，缓解 Context Rot，提升质量。
6. **成本可控**：集中式预算、限流、缓存、模型分层，把 Token 花在刀刃上。
7. **可观测可回放**：全链路 Trace + 轨迹回放，问题可定位、可复现。
8. **协作能力**：支撑 Planner/Coder/Reviewer 等多角色深度协作完成复杂任务。
9. **可持续运行**：外置状态 + 检查点，支持长时运行任务与断点恢复。
10. **异构支持**：不同节点可跑不同模型/角色，灵活匹配任务需求。

## 挑战与权衡

| 挑战 | 说明 | 缓解 |
|------|------|------|
| **系统复杂度高** | 分布式 + 非确定性，运维门槛高 | 完善可观测性、渐进式建设 |
| **状态一致性** | 并发读写记忆/状态易冲突 | 版本控制、乐观锁、幂等设计 |
| **调试困难** | 非确定性，难复现 | 轨迹回放、固定种子、录制回放 |
| **成本易失控** | Agent 会「自主」多轮调用 | 预算护栏、三道保险丝 |
| **上游是真瓶颈** | LLM API 配额限制吞吐 | 多 Key/多供应商、限流、缓存 |
| **编排器单点** | 中心化拓扑的风险 | HA 多副本、状态外置 |
| **过度工程** | 小规模不需要集群 | 从单机起步，按需演进 |

---

## 选型与落地清单

**从 0 到 1 的推荐路径：**

1. **单 Agent + 队列**：先用消息队列 + 单/少量 Worker，验证任务可异步化。
2. **无状态化 + 外置状态**：把会话/上下文移出进程到 Redis/DB。
3. **加编排器**：任务拆解、结果聚合、多角色协作。
4. **加工具网关 + 治理**：统一鉴权、限流、审计。
5. **上 K8s + 自动伸缩**：KEDA 按队列伸缩，做 HA。
6. **建可观测性**：Trace、指标、成本、轨迹回放。
7. **加保险与优化**：三道保险丝、模型分层、缓存、预算护栏。

**技术组件参考选型：**

| 能力 | 候选 |
|------|------|
| 编排/工作流 | LangGraph、Temporal、自研 DAG 引擎 |
| 消息队列 | Kafka、RabbitMQ、NATS、Redis Stream |
| 状态/缓存 | Redis、PostgreSQL |
| 向量/记忆 | pgvector、Milvus、Qdrant |
| 编排调度 | Kubernetes + HPA/KEDA |
| 可观测 | OpenTelemetry + Langfuse/自研轨迹 |
| 工具协议 | MCP + 自建工具网关 |

## 常见误区

- **误区 1：把「多开 Agent」当成集群。** 没有调度/状态/容错/可观测，只是多进程，不是集群。
- **误区 2：Worker 里存状态。** 一旦有状态就无法弹性伸缩与故障恢复。
- **误区 3：用 CPU 指标伸缩。** Agent 大部分时间在等 LLM，CPU 低但任务积压，应按队列深度伸缩。
- **误区 4：无限扩 Worker。** 真正瓶颈往往是上游 LLM API 配额，先解决限流与多供应商。
- **误区 5：不设预算与终止条件。** Agent 会自主循环，极易 Token 爆炸，必须有护栏。
- **误区 6：小规模也上重型集群。** 过度工程；从单机 + 队列起步，按需演进。
- **误区 7：忽视可观测性。** 非确定性系统没有 Trace 就是黑盒，出问题无从下手。

## 小结

Agent 集群是把单 Agent 能力工程化、规模化、生产化的运行底座：**编排层解决怎么分工、调度层解决怎么跑、状态与记忆层解决怎么记、工具与治理层解决怎么安全用、可观测与容错层解决怎么运维**。

落地心法：**Worker 无状态、状态全外置、按队列伸缩、上游是瓶颈、预算加护栏、全链路可观测、从简到繁渐进演进。**
