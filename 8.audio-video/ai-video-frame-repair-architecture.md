# AI 视频抽卡补帧：局部修复与候选生成架构设计

> 面向已生成视频中的穿模、肢体异常、局部物体变形、纹理破损和短时闪烁。本文讨论如何把“不断抽卡补救”实现为可控、可计费、可回退的视频后期能力。

---

## 1. 问题定义与建设目标

### 1.1 什么是抽卡补帧

“抽卡补帧”不是把任意一张生成图直接替换进视频，而是在受限时间段内围绕原视频、问题区域和参考帧生成多个候选片段，再选择一个动态播放自然的结果。

一个可接受的候选必须同时满足：

- 问题区域得到修复，例如手指分离、遮挡关系正确、物体不再穿模。
- 非问题区域尽量保持原样，人物身份、服饰、构图和光照不能明显漂移。
- 修复片段第一帧和最后一帧能与原视频拼接，正常速度播放时没有跳变、闪烁或拖影。
- 每次生成都可追溯到输入素材、遮罩、提示词、模型版本、参数和成本。

### 1.2 首期范围

支持用户手动指定问题区间与问题区域；系统生成候选、供用户比较并合成回原视频。首期不依赖自动检测穿模，也不承诺用单一模型修复所有姿态和遮挡问题。

| 问题类型 | 首选策略 | 说明 |
| --- | --- | --- |
| 单个坏帧或两帧坏帧 | 相邻帧重建 | 原视频前后帧均正确时成本最低 |
| 2–5 秒局部变形 | 局部编辑 + 视频候选生成 | 最主要的“抽卡”场景 |
| 姿态、动作路径整体错误 | 镜头级重生成 | 不能只修改一个局部区域 |
| 长时间人物身份漂移 | 人工拆分为多个短任务 | 以锚点帧和短片段降低漂移 |

### 1.3 非目标

- 首期不训练自有视频生成基础模型。
- 首期不自动替用户做最终选择，质量排序只用于缩小候选范围。
- 不把通用视频插帧当作结构性错误的修复手段；前后帧本身错误时，插帧只会延续错误。

## 2. 总体架构

```text
┌────────────────────── 编辑端 ──────────────────────┐
│ 时间轴选区 · 区域遮罩 · 关键帧编辑 · 候选对比 · 提交 │
└────────────────────────┬───────────────────────────┘
                         │ RepairRequest
┌────────────────────────▼───────────────────────────┐
│ 修复编排服务                                         │
│ 任务校验 · 策略选择 · 预算预占 · 模型路由 · 重试控制 │
└───────┬───────────────────┬─────────────────┬───────┘
        │                   │                 │
        ▼                   ▼                 ▼
┌──────────────┐    ┌──────────────┐  ┌────────────────┐
│ 帧处理服务    │    │ 候选生成服务  │  │ 质量评估服务    │
│ 解码/抽帧/遮罩│    │ 云 API/自部署 │  │ 接缝/漂移/排序  │
└──────┬───────┘    └──────┬───────┘  └───────┬────────┘
       │                   │                  │
       └──────────┬────────┴─────────┬────────┘
                  ▼                  ▼
             对象存储            元数据与账本
                  │                  │
                  └──────► 合成导出服务 ◄────┘
                           保留原音频、拼接、编码
```

核心原则：

1. **生成范围最小化**：只裁剪问题前后必要的上下文，模型只处理待修复区间。
2. **候选与成片分离**：候选永不覆盖源片，只有用户选中后才创建新的成片版本。
3. **模型适配层隔离供应商**：业务只认识“修复任务”和“候选”，不直接依赖某个模型的请求格式。
4. **预算前置**：提交前先估价和预占预算，达到次数或金额上限后停止生成。
5. **保留可复现信息**：可从任何候选还原当次输入，支持重跑、审计和模型效果回归。

## 3. 修复任务与状态机

### 3.1 数据模型

```ts
type RepairMode = 'interpolate' | 'video_edit' | 'shot_regenerate';

interface RepairRequest {
  id: string;
  sourceVideoVersionId: string;
  range: { startMs: number; endMs: number };
  maskTrackId?: string;                 // 逐帧遮罩；没有时为镜头级重生成
  anchorFrames: Array<{ timeMs: number; assetId: string }>;
  prompt: string;
  negativePrompt?: string;
  mode: RepairMode;
  candidateLimit: number;
  budgetLimitCents: number;
  status: 'draft' | 'queued' | 'generating' | 'reviewing' |
          'selected' | 'compositing' | 'completed' | 'failed' | 'cancelled';
}

interface RepairCandidate {
  id: string;
  repairRequestId: string;
  provider: string;
  model: string;
  seed?: string;
  parameters: Record<string, unknown>;
  videoAssetId: string;
  previewAssetId: string;
  estimatedCostCents: number;
  actualCostCents?: number;
  scores: { boundary?: number; identity?: number; temporal?: number; prompt?: number };
  status: 'queued' | 'running' | 'ready' | 'rejected' | 'failed';
}
```

### 3.2 状态流转

```text
draft → queued → generating → reviewing → selected → compositing → completed
                 │              │              │
                 └── failed     └── cancelled  └── 回到 reviewing（重新选择）
```

- `queued`：参数和预算校验已通过，等待计算资源。
- `generating`：模型服务异步生成，一个任务可对应多个候选。
- `reviewing`：候选生成结束，系统提供质量排序和 A/B 播放比较。
- `selected`：用户选中候选，锁定候选内容和参数。
- `compositing`：按时间码拼接回原视频并保留原始音频。

任务、候选和导出版本都采用不可变记录。再次修复产生新的 `RepairRequest`，而不是修改历史任务。

## 4. 关键处理流程

### 4.1 单帧修复：相邻帧重建

适用于第 `n` 帧异常、`n-1` 和 `n+1` 正常的情况。系统将任务路由到光流或帧重建服务，再检测修复帧与相邻帧的差异。

```text
原视频 → 解码 n-1 / n / n+1 → 光流估计 → 生成替代帧 → 接缝评分 → 合成
```

这类任务无需生成式视频模型，延迟和成本最低。两个人物交叉、快速镜头移动或遮挡变化时，光流可能产生拉扯，需要降级到局部生成或人工处理。

### 4.2 局部抽卡：关键帧先行，再生成视频

这是推荐的默认流程。

```text
选定时间段与遮罩
        ↓
抽取问题最明显的关键帧
        ↓
图像局部编辑：生成 K 张静态候选
        ↓
用户或质量排序选出 1 张锚点图
        ↓
视频编辑：原短片段 + 锚点图 + 提示词 → 生成 N 段候选
        ↓
候选评分、对比、选中、回写原视频
```

关键帧先确认“要修成什么样”，避免把高成本视频抽卡浪费在明显不合格的形体和纹理上。遮罩需要向外扩张少量像素并羽化，以给模型重建边缘、阴影和遮挡关系的空间；遮罩过大则会增加人物漂移风险。

提示词只描述修复目标和必须保持不变的元素。例如：`修复右手五指和手掌结构，保持人物脸部、衣服、镜头、动作速度、背景和光照不变。` 负向约束可包括：`不要改变人物身份，不要增加手指，不要改变镜头角度。`

### 4.3 镜头重生成

当原视频中动作关系本身错误，例如人物手臂从物体内部穿过、人物转身后服装完全变化，系统应把问题升级为镜头重生成。输入包含首尾锚点、人物和风格参考图、目标动作描述，以及原片段的相机运动摘要。

首期限制镜头重生成的最大长度，例如 5–10 秒。超过该长度时拆为带重叠的子任务，再由人工选择衔接点。

### 4.4 合成与音频处理

1. 对候选视频重采样到原片的帧率和分辨率。
2. 按时间码裁出有效区间；前后增加少量过渡帧检查接缝。
3. 默认复用源片音频。若重生成改变口型或画面内音源，标记为“需重新配音”，不能静默替换。
4. 生成预览版供逐帧与实时播放检查，确认后输出高码率或中间格式成片。

## 5. 模型接入与自研路线

### 5.1 第三方 API：首期推荐

接入层定义统一的 `VideoRepairProvider`：

```ts
interface VideoRepairProvider {
  estimate(input: ProviderRepairInput): Promise<CostEstimate>;
  submit(input: ProviderRepairInput): Promise<{ externalTaskId: string }>;
  getStatus(externalTaskId: string): Promise<ProviderTaskStatus>;
  cancel(externalTaskId: string): Promise<void>;
}
```

供应商适配器负责上传素材、轮询异步任务、下载结果、解析实际费用和错误码；编排服务不向浏览器暴露供应商 API Key。

以 Runway Dev 为例，Aleph 2.0 支持将已有视频与可选时间位置关键帧图像结合进行视频编辑，输入视频为 2–30 秒、最高 1080p/30fps。其 API 价格为 28 credits/秒，每次至少 56 credits；开发者积分价格为 $0.01/credit。实际接入前需要以目标素材测试成功率、延迟和供应协议。[Runway API 变更记录](https://docs.dev.runwayml.com/api-details/api_changelog/) · [Runway 价格](https://docs.dev.runwayml.com/guides/pricing/)

建议至少支持两家视频模型服务，并通过路由策略选择：

| 路由条件 | 策略 |
| --- | --- |
| 单帧异常且相邻帧稳定 | 本地光流，不调用云模型 |
| 需要可控局部编辑 | 首选带关键帧控制的视频编辑模型 |
| 成本优先、低风险素材 | 先出低成本预览，满意后再生成高质量版本 |
| 供应商失败、超时或内容拒绝 | 切换备选服务；保留用户任务和预算 |

### 5.2 自部署：适合高频、封闭场景

自部署建议先建设两类能力：

- **视频补全/移除**：基于遮罩从时空邻域补齐背景，适合移除错误物体、补背景和短时瑕疵。
- **图像局部编辑 + 视频驱动**：先生成稳定锚点图，再用视频生成模型延续运动，适合需要改变手、脸、服装局部结构的场景。

开源 ProPainter 可处理视频补全与物体移除，但官方许可仅限非商业用途，不能直接用于商业产品；其 720p、80 帧的 FP16 推理估计需要约 25GB 显存，因此不能直接假设为低成本方案。[ProPainter 项目与许可](https://github.com/sczhou/ProPainter)

```text
API Gateway → Repair Orchestrator → GPU Queue → Model Worker
                                      │              ├─ Mask/Tracking Worker
                                      │              ├─ Inpainting Worker
                                      │              └─ Video Generation Worker
                                      └──────────────→ Object Storage
```

模型 Worker 不直接访问业务数据库；仅通过短期签名 URL 读取输入和写入输出。GPU 队列按显存、时长、分辨率和优先级调度，避免大任务阻塞交互式短任务。

### 5.3 不建议首期训练基础模型

自训需要合法的带遮罩、修复目标、时间连续性标注数据，也需要针对身份一致性、人体结构、遮挡关系和视频连续性建立评测集。首期更有价值的投入是积累修复请求、用户选择结果和失败标签；这些真实数据才是后续微调或模型选型的基础。

## 6. 成本控制与容量规划

### 6.1 成本公式

每个修复任务的预算应由系统预估，而不是由用户无限点击生成。

```text
任务成本 = 关键帧候选成本
         + 视频候选数 × max(模型最低计费时长, 修复区间时长) × 单位秒成本
         + 存储、转码与导出成本
```

以 5 秒局部修复、10 张 720p 关键帧、3 个视频候选为例：若关键帧每张 5 credits，视频编辑模型 28 credits/秒，则：

```text
10 × 5 + 3 × 5 × 28 = 470 credits ≈ $4.70
```

这是一次任务的模型消耗示例，不包含税费、存储、带宽和人工审核，也不代表每个候选都会合格。

### 6.2 控制策略

- 默认候选数：关键帧 4 张、视频 2 段；用户明确追加时再增量预占预算。
- 先使用低分辨率或低成本模型筛选，再对选中候选出最终规格。
- 限制单次修复区间长度，过长区间强制拆分。
- 任务按用户、项目和组织设置日预算、月预算与并发上限。
- 供应商回调的实际费用写入不可变账本；预估与实际差异触发告警。
- 对重复输入、同一参数和已失败的配置做去重提示，避免重复收费。

## 7. 质量评估与可观测性

### 7.1 自动评分只做排序

| 指标 | 检测方法 | 用途 |
| --- | --- | --- |
| 接缝一致性 | 候选首尾帧与原视频邻帧的特征差异、光流误差 | 排除明显跳帧 |
| 时间连续性 | 帧间闪烁、局部纹理抖动、运动轨迹异常 | 排除“单帧好看、播放异常” |
| 身份一致性 | 人脸、服装、主体分割和视觉嵌入相似度 | 降低人物漂移 |
| 目标符合度 | 问题区域是否消失、提示词图文匹配 | 排除未修复结果 |
| 非目标保真 | 遮罩外区域与原片差异 | 防止无关区域被重画 |

自动分数不能替代人工确认，尤其是手部、遮挡和高速运动。界面必须支持原片/候选同步播放、逐帧查看、局部放大及候选并排比较。

### 7.2 关键指标

- **修复接受率**：用户最终选中候选的任务数 / 已完成任务数。
- **三次内接受率**：衡量默认抽卡次数是否合理。
- **单个接受结果成本**：总模型成本 / 最终选中候选数。
- **中位完成时长**：从提交至候选可审阅的时长。
- **回退率**：选中候选后又恢复原视频或再次修复的比例。
- **供应商错误率与超时率**：按模型、分辨率和任务类型拆分。

日志必须关联 `repairRequestId`、`candidateId`、源视频版本、模型版本、提示词模板版本、成本、时延和用户选择，不记录超过业务需要的原始敏感内容。

## 8. 失败处理与降级

| 失败场景 | 处理方式 |
| --- | --- |
| 模型任务失败或超时 | 标记候选失败；在未超过预算和尝试次数时切换备选服务 |
| 模型返回时长或分辨率不符 | 转码规范化；超出误差阈值则拒绝候选 |
| 遮罩跟踪失败 | 退回手工关键帧标注，不自动扩大到全画面 |
| 候选接缝不合格 | 降低排序，提示用户扩大上下文或改用镜头重生成 |
| 超预算 | 停止新生成，保留已完成候选，允许调整预算后继续 |
| 合成导出失败 | 不影响候选记录；可从选中候选重新发起合成任务 |

## 9. 分阶段落地建议

### 阶段一：可用 MVP

- 手动时间轴选区、区域遮罩和关键帧上传。
- 一个第三方视频编辑服务、一个图像编辑服务。
- 任务编排、异步状态、候选预览、人工选择和无损回退。
- 成本预估、候选次数上限、实际账本与基础日志。

### 阶段二：质量与效率

- 关键帧局部编辑工作台、遮罩跟踪、自动质量排序。
- 多供应商路由、失败切换和低成本预览策略。
- 单帧光流修复和自动策略推荐。
- 接缝与时间连续性评测，建立离线回归集。

### 阶段三：规模化与自部署评估

- 基于真实接受率、调用量、时延与单个接受结果成本决策是否自部署。
- 在授权允许的前提下部署补全模型，优先覆盖背景修复和单帧异常。
- 积累经用户同意的数据集，评估领域微调是否能显著提高特定素材类型的成功率。

## 10. 决策结论

首期采用“自研任务编排、候选管理、合成与质量闭环 + 第三方视频编辑 API”的组合路线。它能最快验证两件最关键的事：局部修复的真实接受率，以及一个合格结果所需的实际抽卡成本。

自部署应在调用量稳定、数据边界明确、模型许可满足商业用途，并且云 API 的单位成功成本持续高于自建服务全成本后启动。基础模型自训不应作为首期项目目标。
